# ADR-001: MongoDB для заказов интернет-магазина

**Статус:** принято для учебного прототипа.

## Контекст
Нужно получать заказ вместе с позициями и исходными ценами, выбирать заказы клиента/статуса/периода, получать аналитику по категориям.

## Решение
MongoDB с одной коллекцией `orders`: поля `_id`, `customer_id`, `created_at`, `status`, `total_kzt`, `items[]`. Каждая позиция хранит `product_id`, `name_snapshot`, `category_snapshot`, `unit_price_kzt_snapshot`, `quantity`, `line_total_kzt`. Цены — целые KZT. Агрегации выполняются `$match` → `$unwind` → `$group` → `$sort`.

## Альтернативы
- PostgreSQL: строгие связи и транзакции, но позиции потребовали бы отдельной таблицы и JOIN для получения заказа.
- Redis: подходит для кэша, не выбран для единственного постоянного хранилища заказов.
- MongoDB: удобно хранить и возвращать заказ единым документом; демонстрирует embedding и агрегирование.

## Индексы
`(customer_id, created_at DESC)`, `(status, created_at DESC)`, `items.category_snapshot`. Диапазон дат Q4 при росте нагрузки может потребовать отдельного индекса `created_at`; в учебном примере данные малы.

## Компромиссы и ограничения
Embedded items эффективны при небольшом числе позиций; документ MongoDB имеет ограничение 16 MB. Денормализация фиксирует историческую цену, а не текущую из каталога. Клиент должен контролировать переходы статусов, операции оплаты и идемпотентность в реальном проекте. Продажи учитываются по статусам paid/shipped/delivered — это учебное бизнес-правило, не бухгалтерское признание выручки. В образце не реализованы аутентификация, конкурентное резервирование запасов и внешняя платежная система.
